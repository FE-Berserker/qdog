# qdog

四足机器狗 MuJoCo 动作仿真与关节载荷分析流水线。

对一台四足机器狗自动完成 **行走 / 奔跑 / 跳跃 / 前扑 / 跌落** 五个基本动作的仿真,
以及 **满载行走 / 爬坡 / 满载爬坡 / 静站载重** 载荷地形工况、
**侧向推搡 / 侧跌倒落 / 关节堵转** 异常失效工况 (按设计工况统计的工况矩阵扩展),
提取每个关节的 **扭矩、弯矩、受力(轴向/剪切)**, 生成 **动作视频** 和 **Excel 表格**,
最后跨动作汇总 **载荷包络** —— 用于关节/轴承/结构件的设计选型校核。

## 工作流程 (agent 必须遵守)

本流水线是 **逐动作人工确认** 流程, 不是批处理。唯一默认路径:

1. **一次只跑一个动作**: `python run_pipeline.py --motions <key>`
2. 跑完立刻把 **check** 交到对话里, 三件缺一不可:
   - **指标摘要**: 速度 / 姿态波动 / GRF 峰值 / 力矩峰值 / 是否跌倒
   - **视频**: `results/<robot>/<key>/video.avi` 与 `video_preview.gif` (点开即看),
     必要时给 `video_first/mid/last.png` 抽查帧
   - **自检结论**: 步态是否对称、有无打滑/拖地、腾空相位、峰值是否超额定
3. **停在这里等回复**。用户说 "确认 / 可以, 下一个" 才继续; 用户提调整意见 (自由文本,
   如 "前扑再远一点") → 改 `quad_pipeline/motions.py` 参数 → 重跑 **同一个** 动作,
   重新交付 check。确认门之所以在对话层而不在终端: 调整意见是自由文本, 终端选项装不下
4. 用户说 "全部跑" 时: 仍按 1~3 **逐个执行、逐个交付 check**, 只是不再等待回复;
   仅当用户明确说 "直接跑完, 不用给我看" 才可合并交付
5. 全部动作确认后, 才汇总载荷包络 (`--envelope-only` 可复用已有数据)

**禁止**: 未交付 check 就连跑下一个动作; 用不带 `--motions` 的命令一次跑全部动作;
在动作未确认时引用其数据下结论。

确认门的经济意义: 单动作含视频约 1.5 分钟、50 MB (实测 walk 74 s / trot 82 s / jump 32 s),
12 个动作批跑约 20 分钟 —— 第一个动作的步态不对, 后面全部返工。

脚本自身不暂停不提问, 每个动作的数据 (trace/表格/视频) 在仿真结束即刻落盘, 中途调整
不丢已确认结果; 但 **agent 驱动时必须走上面的确认门** —— "能批跑" 不等于 "可以跳过确认"。
目录里没有 "哪些动作过了人工确认" 的状态标记, 中断后以对话记录为准。

## 功能特性

- **五个内置基本动作**(均在 Unitree A2 上实仿调定): 四节拍行走(0.47 m/s)、对角小跑
  (1.33 m/s)、原地跳跃(起跳 2.96 m/s)、前扑跳跃(腾空 0.448 s 前进 **0.604 m**,
  v3 控制器 "跑动中弹射", 见下文扩展)、30 cm 跌落缓冲(冲击峰值 11.9 倍体重, 四足同时触地)
- **四个载荷/地形工况**(工况 × 负载矩阵, 对应设计工况统计中"额定扭矩与热平衡"、
  "结构静强度"两类决定性边界): 满载行走(25 kg, 0.40 m/s)、20° 爬坡(实测上行 0.20 m/s)、
  满载爬坡(15°+25 kg, 实测上行 0.41 m/s)、静站载重(100 kg, 总反力 1375 N = 140 kg 重量)。
  负载/坡度为 Motion 类属性 (`PAYLOAD`/`SLOPE_DEG`), 派生即新工况;
  坡度用重力矢量倾斜法(力学上与上坡严格等价, 视频渲染时反向旋转并放入
  斜坡障碍物, 坡角直观可见; 负载工况视频在背部挂货箱可视化)
- **三个异常/失效工况**(可靠性设计与安全功能输入): 侧向推搡(trot 中 50 N×0.25 s
  躯干冲击, 姿态峰峰值 9.0°/4.3°, 横向速度增量 +0.28 m/s 与理论冲量吻合)、
  侧跌倒落(0.30 m+25° 侧倾非受控跌落, 冲击 4.8 倍体重, 右腿先触地且弯矩/剪力为全工况最高)、
  关节堵转(膝关节 equality 焊接卡滞+下蹲施压, 从 1.46 s 起持续饱和 180 N·m 共 2.54 s,
  驱动器 I²t 热保护设计输入)
- **关节载荷全口径**: 绕轴驱动扭矩(电机承担) + 弯矩(轴承/壳体承担) + 轴向力 +
  剪切力; 弯矩用 MuJoCo 原生 force/torque 传感器在关节锚点直接测量,
  经双摆数值验证(绕轴分量与执行器+被动力矩精确一致, 见 `verify_sensor.py`)
- **完整产物**: 每动作输出全量时序 CSV(2 ms, 含重力/被动/约束/惯性分解)、
  关节受力.xlsx、关节弯矩.xlsx、扭矩/运动学/弯矩曲线 PNG、双机位跟踪视频
  (纯 Python MJPEG-AVI 编码, 不依赖 ffmpeg; 有 ffmpeg 时另出 MP4;
  逐帧流式 JPEG 编码, 不把全部帧驻留内存; `t_win=(t0,t1)` 可只渲染指定时间窗,
  用于冲击/瞬态工况 —— 全程视频里事件可能只占 3%, 单独出窗口版才看得清)
- **动作自检** (`check_motion.py`): 从 trace 做足端正运动学, 输出步态占空比/周期、
  左右对称性、触地相足端漂移(打滑)、摆动相接触(拖地)、腾空占比、航向漂移、峰值裕度 ——
  交付 check 的"自检结论"由此得出, 不靠肉眼
- **载荷包络**: 跨工况取每关节各指标最大值并标注来源工况, 附工况×关节矩阵热力图、
  占额定比列与参考判据(落地冲击约 2.3×额定属正常、电机峰值 5~10×、建议 3×余量)
- **可扩展**: 新动作 = 注册一个控制器子类; 新机型 = 注册一个 RobotConfig

## 安装

```bash
pip install -r requirements.txt
```

需要自行准备机器人 MuJoCo 模型(见下文"机器人模型")。

## 快速开始

```bash
python run_pipeline.py --motions walk   # 【推荐】逐动作: 跑一个 → 交 check → 等确认
python run_pipeline.py --motions drop   # 只跑跌落 (快速验证, 约 1 分钟)
python run_pipeline.py --motions walk_full slope slope_full stand_load --skip-video
                                       # 只跑载荷/地形工况
python run_pipeline.py --skip-video    # 跳过视频渲染
python run_pipeline.py --list          # 查看已注册机型/动作
python run_pipeline.py                 # ⚠ 全量批跑 (约 20 分钟); 仅当用户明确要求
```

                             + 四足反力 + 支撑标志 + 速度指令
  关节受力.xlsx              扭矩时序 + 统计 + 工况指标
  torques.png / motion.png   扭矩曲线 / 运动学+地面反力曲线
  wrench.csv                 12 关节 6 分量相互作用 wrench

  video_preview.gif          GIF 预览 (点开即看)
  video_first/mid/last.png   抽查帧
  --- 瞬态工况应额外交付 (push/fall/stall: 事件只占全程极小比例) ---

## 扩展

**新增动作** (`quad_pipeline/motions.py`):

```python
@motion("my_move", "我的动作", "工况说明", t_end=6.0, win=(1.0, 6.0))
class MyMove(CaseSimBase):
    def init_pose(self): ...
    def step(self): ...        # 每步算 12 关节目标 -> self.apply_pd(q_tgt, kp, kd)
```

**新增载荷/地形工况变体** (派生覆盖类属性即可):

```python
@motion("trot_full", "满载奔跑", "对角小跑 + 25 kg", t_end=8.0, win=(2.8, 8.0))
class TrotFullMotion(TrotMotion):
    PAYLOAD = 25.0             # 躯干附加负载 kg (挂于 cfg.trunk_body 质心)
    SLOPE_DEG = 0.0            # 等效坡度 deg (重力矢量倾斜法)
    # 可选: R_ST 站姿腿长 / K_FB / XC_LIM / XA_BOOST 步态参数
    # 可选: SCENE_EXTRA 场景定制片段 (如堵转的 equality 焊接), 自动生成 scene_<key>.xml
```

注意: 时钟步态 PD 控制器的扭矩预算有限 —— 30° 坡即使空载也无法持续上行
(执行器饱和), 故爬坡定为 20°、满载爬坡定为 15°(均为实仿验证的真实上行);
更陡坡度+满载需要整机姿态/力分配规划控制器。重载保持类工况(如静站载重)
需加大 PD 刚度; 更陡/更重的爬坡工况需要更强的控制器, 或按设计需要降低坡度考核值。

**新增机型** (`quad_pipeline/config.py`):

```python
register(RobotConfig(name="go2", model_xml="...", mesh_dir="...",
                     L1=..., L2=..., foot_r=..., r_max=..., r_stand=...,
                     rated=(..., ..., ...)))
```

关节命名约定 `{leg}_{part}_joint` (leg=FL/RL/FR/RR, part=hip/thigh/calf);
不一致时改 `joint_fmt`/`act_fmt`/`body_fmt` 模板即可。动作参数(步态周期/
速度/蹬伸深度等)为各 Motion 子类的类属性, 换机型时派生覆盖。

**改控制器** (`LeapMotion` v3 为例, 前扑距离 0.267 -> 0.604 m):

姿势步态 PD 控制器做"深蹲蓄力->爆发蹬伸"时, 助跑一快就必然失败。机理三条, 对应三种改法:

1. **收腿/蹬伸段身体前进量超出腿的工作空间** -> 后腿被拉离地面, 只剩前腿蹬, 低头栽倒。
   改法: 足端按躯干前进量钉地 (躯干前进多少, 足端相对髋后移多少), 并把整段压缩到
   身体前进量约 0.30 m
2. **该段无姿态反馈** -> 地面反力落在质心之后, 低头力矩发散。改法: 后腿只负责推进,
   前腿保持支撑长度并承担俯仰/横滚配平 (与真实犬科起跳分工一致)
3. **触发时机撞上摆动相** -> 单侧支撑侧翻。改法: 触发同步到步态相位 (如"两条后腿
   同时处于支撑相"的窗口), 而不是固定时刻

两条经验: **反向下沉 (countermovement)** 能加长腿部做功行程 —— 执行器扭矩受限时
行程越长总冲量越大; **空中滚转**需单独控制 (起跳带的角速度会积分到 20 度以上),
用四腿髋外展同向摆动做角动量交换即可压下来。

## 已知限制 (2026-09 全 12 工况实测)

1. **无横向/偏航闭环**: 控制器只有腿长与俯仰/横滚配平, 直线动作会跑偏 ——
   `trot` 航向漂移 -12.2 度 (横移 1.51 m)、`slope_full` -49.1 度 (横移 1.47 m)、
   `slope` +9.7 度; 载重与坡道会放大偏差 (walk_full 漂移为空载的 4 倍)。
   要做能走直线的平台需补横向速度/偏航闭环
2. **`push` 不是干净的抗扰测试**: trot 自身横向漂移 (-0.27 m/s) 与推搡冲量 (+0.28 m/s)
   量级相同且方向相反, 二者几乎抵消, 所以"恢复"里混着"本来就往外飘"的成分
3. **包络主导工况是冲击类**: 驱动/弯矩/剪力/轴向四项最大值全部来自 `leap`/`fall`/`drop`,
   无一项来自行走类。`RR_calf` 驱动包络 **187 N·m = 104% 额定** (唯一超额定项) ——
   传感器测的是关节界面总轴向力矩 (执行器限幅 + 转子惯量/约束内务项),
   **结构件应按 >100% 额定设计**, 按 100% 会偏危险
4. **`leap` 落地不对称**: 腾空残留约 16 度滚转, 右腿先着地、左腿晚约 0.5 s, 航向漂移 -14.9 度
5. **改步态参数注意继承**: `WalkMotion` 的改动会被 `TrotMotion`/`SlopeMotion` 继承,
   单独标定的动作需显式隔离 (如 `TrotMotion.SW_SCALE = 1.0`、`SlopeMotion.DUTY = 0.75`),
   否则会连坐破坏其标定
